Contexte & Problématique

Pourquoi ce Projet ?

🏚️

Absence de présence numérique pour les PME

En Tunisie, 78% des petits commerces n'ont aucun outil digital moderne. Aucune plateforme centralisée pour gérer produits, commandes, livraisons ou customer relations.

🔎

Découverte de services fragmentée et inefficace

Les consommateurs dépensent en moyenne 45 min par semaine à chercher services/produits locaux vs 5 min sur des plateformes intégrées. Gap d'expérience énorme.

💳

Gestion financière peu professionnelle

Aucun dashboard centralisé pour les commerçants. Suivi des commandes, remboursements et transactions disséminés sur plusieurs outils incompatibles.

🌍

Gap technologique sur le marché régional

Aucune solution marketplace moderne ne couvre le marché B2C tunisien avec des outils SaaS professionnels intégrant IA moderne et paiements omnicanal.

Focus Technique · Authentification

Système d'Authentification Sécurisé

1

POST /api/auth/login

Valide credentials via Supabase SSR, génère session sécurisée côté serveur, retourne JSON response.

2

POST /api/auth/magic-link

Crée lien temporaire via Admin Client, envoie email HTML personnalisé via Resend avec expiration 15min.

3

GET /api/auth/callback

Échange token OTP, valide session, établit cookies HTTP-Only, redirige automatiquement utilisateur.

4

GET /api/auth/session

Valide session côté serveur sans exposer tokens au client JavaScript, retourne user payload.

5

POST /api/auth/logout

Invalide session, supprime tous les cookies sécurisés, empêche réutilisation token.

🔒

Toute la logique auth est 100% côté serveur via API Routes. Jamais exposée au bundle JavaScript client pour éliminer risques XSS.

🛡️

Middleware Protection

Fichier `middleware.ts` intercepte chaque requête, valide session, redirige users non-authentiques avant rendu page.

🍪

HTTP-Only Cookies

Tokens Supabase stockés dans cookies HTTP-Only inaccessibles au JavaScript client, éliminant risques XSS/CSRF.

🔑

OAuth Google

Intégration OAuth complète permettant login via Google avec redirect automatique et création user si nouveau.

Background Workers

Tâches Asynchrones Resilientes

🔄

Payment Retry Worker

Trigger: 2 min après création commande
Action: Vérifie confirmation paiement
Resilience: QStash retry exponential si échec

🔗

ERP Sync Worker

Trigger: Dès validation commande
Action: Envoie données à API ERP externe
Resilience: Max 5 retries, notifie si fails

💸

Async Refund Worker

Trigger: User demande remboursement
Action: Traite refund sans bloquer UI
Resilience: Garantie livraison même offline

✅

Admin Webhooks

Endpoints: POST /api/webhooks/confirm, /refund, /status
Security: Bearer token validation
Signature: Upstash verification

⚡

Tous les workers utilisent Upstash QStash avec signatures cryptographiques pour garantir que seul le serveur QStash peut les déclencher, éliminant risques de spoofing.

Défis & Solutions

Obstacles Surmontés

⚡

Challenge: Performance de la recherche sémantique

Embeddings 768-dim via Gemini lents à générer pour chaque query

Solution: Mis en cache les embeddings fréquents via Upstash Redis. Query time réduit de 2000ms à <50ms. Cache invalidation smart.

🔐

Challenge: Sécurité des données marchands

Comment garantir qu'un marchand ne voit QUE ses propres données?

Solution: RLS policies PostgreSQL au niveau application + middleware auth stricte. Zero-trust architecture. Audit logging exhaustif.

⚙️

Challenge: Tâches asynchrones resilientes

Paiements + remboursements peuvent échouer, retry requis sans perdre de données

Solution: Upstash QStash avec signatures cryptographiques + retry exponential. Idempotency keys pour éviter duplicatas. 99.9% uptime garantie.

🌍

Challenge: Support pour langue arabe

Recherche sémantique et indexation doivent fonctionner en arabe

Solution: Gemini embeddings naturellement supportent arabe via UTF-8. No extra work needed. Tested ✓ "قهوة تونسية" fonctionne.

Focus Technique · Auth

Système d'Authentification

1

POST /api/auth/login

Vérifie les credentials via Supabase SSR, crée les cookies de session côté serveur et répond en JSON.

2

POST /api/auth/magic-link

Génère un lien via l'Admin Client Supabase, puis envoie l'email via Resend avec un template HTML personnalisé.

3

GET /api/auth/verify

Échange le token OTP contre une session valide, établit les cookies et redirige l'utilisateur automatiquement.

4

GET /api/auth/session

Valide la session active côté serveur sans exposer les tokens dans le client pour une meilleure sécurité.

5

POST /api/auth/logout

Invalide la session et supprime tous les cookies sécurisés, empêchant toute réutilisation du token.

🔒

Toute la logique d'auth est 100% côté serveur via API Routes, jamais exposée au bundle client React.

🛡️

Middleware de Protection

Le fichier `middleware.ts` intercepte chaque requête et redirige automatiquement les utilisateurs non authentifiés avant que le rendu de page ne commence.

🍪

Session via Cookies HTTP-Only

Les tokens Supabase sont stockés dans des cookies HTTP-Only inaccessibles au JavaScript client, éliminant les risques XSS.

Focus Technique · Workers

Background Workers & Webhooks

🔄

Payment Retry

Planifie automatiquement un worker 2 min après chaque commande pour vérifier la confirmation de paiement. QStash retry si le process échoue.

🔗

Sync Orders ERP

Dès qu'une commande est validée, un job background envoie les données à l'API externe (ERP, comptabilité, livraison).

💸

Async Refund

Le remboursement est traité en tâche de fond sans bloquer l'utilisateur. QStash garantit la livraison même en cas d'indisponibilité API.

✅

Webhook Confirm

Endpoint sécurisé (Bearer Token) permettant à des systèmes externes de confirmer une commande, bypass RLS via Admin Client.

↩️

Webhook Refund

Endpoint POST permettant à un opérateur de déclencher un remboursement programmatiquement depuis n'importe quel système tiers.

🔐

Signature Vérifiée

Les workers sont protégés par `verifySignatureAppRouter` d'Upstash : seul le serveur QStash peut les déclencher.
